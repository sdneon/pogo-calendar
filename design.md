# PoGo Calendar — design notes

## Purpose

To see at a glance which valuable Pokémon are featured on each day of a month, so the user can plan targets and rest days. Valuable means legendary / mythical / Ultra Beast species, or any Pokémon in a Mega, Super Mega, Shadow raid, Dynamax, Gigantamax or Community Day role.

## Parts

- `server.js`: a Node `http` server with no dependencies, bound to 127.0.0.1:8642. It serves `public/`, the API, the icon proxy, and runs the timed refresh.
- `lib/scrape.js`: reads the Leek Duck events list and detail pages.
- `lib/store.js`: the JSON-file store (`data/store-public.json` + `data/store.json`, each written atomically through a temp file and rename).
- `public/calendar.html|css|js`: the page. `public/pokedex.js` is generated by `tools/build_pokedex.js`.

## API

| Method | Path | Body / result |
|---|---|---|
| GET | `/api/events` | `{events[], days{}, lastRefresh, lastError, refreshing}` |
| POST | `/api/events` | new user event → event |
| PUT | `/api/events/:id` | editable fields → event |
| DELETE | `/api/events/:id` | user event: deleted; Leek Duck event: reverted to the Leek Duck copy |
| PUT | `/api/days/:yyyy-mm-dd` | `{rest, note, pokemon[], public}`; an empty day is removed |
| POST | `/api/refresh` | starts a Leek Duck check (202) |
| GET | `/api/public` | what would be published now, vs `public/public.json`: `{current, publishedAt, dropping, upToDate}` |
| POST | `/api/publish` | writes `public/public.json` from the items ticked public → counts |
| GET | `/icon?u=<cdn.leekduck.com url>` | image, cached in `data/icons/` |

Writes must be `Content-Type: application/json`, which forces a CORS preflight. The page's `api()` sends `{}` for body-less writes (Publish, Check Leek Duck); without that they got 415, which broke both buttons until 2026-10-26. Only Origin `null` (the page opened from disk), localhost, or no Origin are allowed. Together these stop other websites from changing the data through the browser.

## Store

`events[id]` holds `{id, source: 'leekduck'|'user', title, type, typeLabel, start, end, url, image, note, hidden, tier, tz, public, from, starred[], hosts[], pokemon[], edited[], ld}`.

- `ld` is the last scraped copy. On each scrape, every field in `FROM_LD` that isn't listed in `edited` is copied from `ld`. Saving an event works out `edited` by comparing each field with `ld`, so changing a field back to Leek Duck's value un-marks it.
- `note`, `hidden`, `tier`, `tz`, `public`, `from`, `starred` and `hosts` are user-only: never in the Leek Duck copy and never marked as edited.
- `starred` holds `"name|act"` keys of starred Pokémon the user didn't add, so starring one leaves `pokemon` following Leek Duck. The page's `markStars()` turns them into `star: true` after loading, and the editor splits them back out on save.
- `hosts` holds trainer meetups: `{host, venue, start, end, map?}`, with times as SGT wall time `yyyy-mm-ddThh:mm` and `map` an optional http(s) link to the venue. They show on the event card as "Meetup: Host @ Venue, time", plus a "Map" link in the day panel only (tooltips vanish on mouse-out, so a link there can't be clicked). The page links `map` only when it's http(s), since imported files reach the static site's layer without the server's cleaning.
- **Two files on disk** (both in git-ignored `data/`), the same merged model in memory:
  - `store-public.json`: `{version: 2, lastRefresh, lastError, events: {id: ld}}`, the Leek Duck copies, rewritten by scrapes;
  - `store.json`: `{version: 2, events, days, dropped}`, only the user's own: user events whole, and for a Leek Duck event an overlay `{id, source, edited, <edited fields>, <user-only fields that are set>}`. Untouched Leek Duck events aren't in it.

  An overlay whose record isn't in `store-public.json` is kept as it is (`orphans`) and joins its event once a scrape or seed brings the record. A version-1 `store.json` (one file, `ld` inside each event) is read as before, copied to `store-v1-backup.json`, and split on the server's first start.
- **Seeding:** at startup the server fetches the live site's `events.json` and adds the Leek Duck records the store lacks. That brings past events into a fresh copy, since Leek Duck lists only current and upcoming ones. Records already in the store are left alone. The site address is `SITE_URL`, else derived from the clone's GitHub remote (`<user>.github.io/<repo>/`). `NO_SEED=1` turns it off. It runs before the startup check, so the scraper also skips detail pages the seed already has.
- **Taking in `public.json`:** `public/public.json` comes from git, but `data/` doesn't, so a new clone starts with an empty store. At startup, and after each scrape, `Store.adoptPublished()` takes in what `public.json` holds and the store lacks. That covers user events not in the store, untouched Leek Duck events (no edits, no user fields) for their patch, and days not in the store. It never overwrites the owner's changes. A user event the owner deleted is listed in `dropped`, so it isn't taken back in before the next Publish. Before 2026-10-27 owner mode never read `public.json`, so Publish from a fresh clone replaced its contents.
- `GET /api/public` also returns `dropping`: published items that Publish would take off the public site. The Public… dialog lists them as a warning.
- Events that drop off Leek Duck's list are kept (history).

`days[yyyy-mm-dd]` holds `{rest, note, pokemon[], public}`.

A Pokémon entry is `{name, dex, icon, act, shiny, bg, region, fromTitle?}`, plus `{mine, star, comment, from?}` for entries the user added. Only those keep a comment or author in the entry; stars on other entries live in the event's `starred`. `act` is an activity key (see below), and `icon` is a Leek Duck CDN URL or empty (the page then builds `pokemon_icon_<dex>_00.png`).

## Scraping Leek Duck (markup as of 2026-10-21)

- **List page** `/events/`: one `span.event-header-item-wrapper` per occurrence.
  - Attributes: `data-event-type`, `data-event-occurrence-id` (used as our id), `data-event-start-date` or `data-event-start-date-check`, and `data-event-end-date`, which only "Happening now" items have.
  - Inside: `a[href]`, an `img`, the title `h2` and `.event-tag-badge`.
  - The same occurrence can appear in more than one section, so items are de-duplicated by id.
- **Detail page**: `div.schedule-row` with `data-kind` set to `single` (`data-start` + `data-end`), or a `start` row followed by an `end` row. The end row's time is also in its `data-start`. Sections are `h2#<section> .event-section-header`, each followed by `li.pkmn-list-item` (icon `img`, `.pkmn-name`, optional `.shiny-icon`). The `shiny` section only marks shiny availability.
- **Times** are local-time strings with no zone (e.g. `2026-10-21T06:00:00`), except a few such as GO Battle League, which carry `+00:00`. They are stored exactly as written; the page reads zone-less ones as wall-clock time in the event's zone (see "Home time").
- **Politeness**: one detail request per second. A detail page is only fetched for events that are new or not yet ended and haven't been fetched in the last 24 h. It's cached per URL within one run. The list is checked every 6 h.
- **Dex numbers** come from the icon file name (`pokemon_icon_483_00.png`, `pm609.fMEGA.icon.png`, `poke_capture_0774_…`).
- **Title-derived Pokémon:** pages with no Pokémon list (Raid Hour, some Max Monday pages) take names from the title, e.g. "Cresselia and Darkrai Raid Hour". Only names that `public/pokedex.js` knows as species are kept. These entries are flagged `fromTitle`. Their shiny flag is copied from an overlapping event that lists the same dex and form (`shareShiny()`), such as the 5★ rotation behind a Raid Hour.
- **Special backgrounds** appear only in prose. Sentences containing "special background" are kept (`bgText`), and a Pokémon gets `bg` when its name appears there and its activity is a raid, Max Battle or research catch. "Dynamax Dialga" counts only for the Dynamax one.
- **Region locks** (`regionOf()`) also come from prose. A line like "Mesprit: Europe, the Middle East, Africa, and India." or "… in the Western Hemisphere" sets `region` to `apac`, `emea`, `americas`, `east` or `west`.
- **Sub-sections:** a main section header is `<h2 id class="event-section-header">`. A plain `<h2 id>` inside it is a sub-section, named `main/sub` (e.g. `raids/max-battles`, `raids/five-star-raids`), so a Max Battles list under "Raids" is classed `dmax` / `gmax`, not `raid`. Before SCRAPE_VERSION 7 they were folded into the main section.
- **Prose** for the rules below (`parseDetail().sentences`) leaves out Pokémon lists and ends a sentence at every heading, paragraph and list item, since headings have no full stop.
- **`mentions(text, name, act)`** decides whether prose names a Pokémon. "Dynamax X" / "Gigantamax X" count only for that activity. "Hisuian X" (or another regional form) counts only for the regional form. The species word is found in the pokédex ("Unown S" → Unown, "Modern Jacket Machamp" → Machamp). With `needForm`, a bracketed form must be named too ("Minior (Green Core)").
- **Debuts** (`debut: 'new' | 'shiny'`): a Pokémon listed in a section whose id contains "debut", or named in a debut clause. Debut clauses come from sentences with "debut", minus "will debut", minus "See …" pointers to another event, and minus "debuts during the Orionids" when the title isn't that shower. Sentences are split at ", and" and ";", and only the parts that mention a debut are kept. "Shiny Greavard makes its debut" gives `'shiny'`.
- **Location Backgrounds** (`lbg: place`, `lbgTicket`): sentences naming a "Location Background" (a photo of the event's city, unlike the clip-art Special Background). The place is read from "a Sendai Location Background", and `lbgTicket` is set when the sentence says ticket holders. Only raid / Max Battle / research catches get it. The tooltip says it's in-person only, never for remote players.
- **Minior Showers** (`dropUndebuted()`): the page lists all seven cores, but each shower debuts one, named in prose ("Green Core Minior debuts during the Orionids."). Only cores debuting in the event's own shower (matched by the title) are kept; while the colour is unannounced, only Meteor Form remains.
- **`SCRAPE_VERSION`:** bump it when parsing changes, so every stored detail page is fetched again once. The server checks Leek Duck at startup when the last check is over 6 h old, or when any unfinished stored event was read by an older version. Before 2026-10-26 it only checked the age, so a restart after a bump did nothing until the next 6-hourly check.

## Activities (pins)

`classify()` in `lib/scrape.js` picks one activity per featured Pokémon. Section ids vary by page (`raids`, `five-star-raids`, `max-battles`, `dynamax-dialga-and-dynamax-palkia`), so the rules match on parts of the id. They are tested in this order:

1. `gmax` / `dmax`: the section id says gigantamax / dynamax; the name starts with Gigantamax / Dynamax; a max-battle section; or, outside a raid section, the title or type is Max Mondays, Max Battles or Dynamax.
2. `supermega` / `mega`: the name starts with "Mega " or "Primal "; the title decides Super Mega.
3. `shadow`: the name starts with "Shadow ", or the raid section of a shadow event.
4. `cd`: Community Day, except its research / ticket / web-store sections (evolutions listed there become `research`).
5. `spotlight`: Spotlight Hour.
6. `hatch`: the title says hatch, or an egg section.
7. `raid`: a raid section, or a raid-type event.
8. `research`, `wild`: research or wild/spawn sections.
9. `event`: anything else.

The same keys, with labels, glyphs and colours, are in `ACTIVITIES` in `public/calendar.js`. The user can change any Pokémon's pin in the editor.

## Campfire meetups

Singapore trainer meetups from Campfire (`campfire.scopely.com/discover`), shown alongside the user's own meetups. Campfire has no public API: `lib/campfire.js` uses the GraphQL API its web page calls without signing in (`niantic-social-api.nianticlabs.com/graphql`, with the page's `Origin` / `Referer`), so it can change or stop working at any time.

- **Fetching** (`fetchCampfire()`), about 70 requests, 1 per second:
  1. Campfire's game events: `marketableCampfireLiveEvents(input: {game: "PGO"})`, named like Leek Duck's ("Chandelure Super Mega Raid Day", "Into the Wild Day 1").
  2. For each, its meetups inside a Singapore box (1.20–1.48° N, 103.60–104.05° E): `meetupMapObjectsByLiveEventIdInLatLngBounds`. One call per game event is nearly complete (12 of 13 in a tile test). The general map query (`realityChannelMapObjectsInLatLngBounds`) returns only a capped sample (3–4 per call), so it isn't used.
  3. Each meetup's details, with only the fields shown: name, address, description, times, location, host's display name, club, game event, attendee count. The attendee list and comments are never requested. Details are reused for 12 h; public, in-box meetups only.

  Meetups that drop off are kept for 90 days after they end (history), like Leek Duck events.
- **Server:** `data/campfire.json` `{fetchedAt, error, meetups[]}`, refreshed at startup when older than `REFRESH_HOURS`, then every `REFRESH_HOURS`, and by **Check Leek Duck**. `NO_CAMPFIRE=1` turns it off (`NO_REFRESH` doesn't, since it's about Leek Duck). `GET /api/campfire` → `{fetchedAt, error, refreshing, off, meetups, mine}`; `PUT /api/campfire/:id` `{going, pokemon}` saves the user's marks in `store.json` (`campfire: {id: {going, pokemon}}`); Publish includes the targets (`public.json` `campfire: {id: {pokemon}}`, by default, no tick), never `going`.
- **Page** (`buildCampfire()`, rebuilt by each `render()` into `CF`): each meetup becomes a meetup `{h, ev}` with `h.campfire` = the record. `ev` is the calendar event of the same name that day: names compared lower-case, letters and digits only, a trailing "Day N" dropped, either containing the other. Otherwise `ev` is a stand-in named after the game event. So Campfire meetups get the pink pin, the attending mark, their own targets, and the day's lines in tooltips, like the user's own.
  - Order in lists (`cfOrder`): attending first, then hosts in `CF_PRIORITY_HOSTS` (display names, any case), then by start.
  - The pin tooltip lists them one line each under "On Campfire (N)", in that order, at most 6.
  - A cell Pokémon's tooltip lists only those the user attends, plus a count of the others.
  - The day panel has a "Campfire meetups" section (`cfCard()`): link to the meetup's Campfire page (`/discover/meetup/<id>`), host and club, a Google Maps link from its coordinates, the description, **Attending?**, and "My targets for this meetup".
  - The header switch **Campfire meetups** (`prefs.campfire`) hides them all.
- **Public site:** `tools/build_site.js` writes `site/campfire.json` `{fetchedAt, meetups}`. In GitHub Actions it fetches, reusing the previous site's `campfire.json` (next to `--known`'s `events.json`) for details and history; if the fetch fails, or `NO_CAMPFIRE` is set, the previous list is kept as it is. With `--from-store` it copies the server's `data/campfire.json`. The static page loads it with `events.json` / `public.json`; a visitor's attending and targets stay in their browser (localStorage `pogoCalendarCampfireMine`). The owner's published Campfire targets (`public.json` `campfire`) show there until a visitor sets their own for that meetup; the owner's attending is never published, and the public preview shows the targets only.

## Static site (GitHub Pages)

The same page runs in two modes. `STATIC` in `calendar.js` is true unless the page is on localhost or opened from disk, and `?static` forces it on.

- **Owner mode:** `serverBackend`, the local server and its store, as described above. Each event and each day has a **public** flag (user-only). **Publish** (`POST /api/publish`) writes `public/public.json` from `Store.publicSnapshot()`:
  - a user event goes in whole (without `ld` or `public`);
  - a Leek Duck event goes in as a *patch* (`edited` plus the edited fields, and `note`/`hidden`/`tier`/`tz`/`starred`/`hosts`);
  - each public day goes in whole.

  Nothing else unflagged is included, except what's published by default (no tick; the Public… dialog lists it): the meetups of a Leek Duck event that isn't public (a `meetupsOnly` patch of `hosts`; `adoptPublished()` takes it in without making the event public), and the owner's targets on Campfire meetups (`campfire`). Meetups on the owner's own private events stay private, since publishing them would reveal the event. `going` (attending) is never published. (Before 2026-10-27 meetups followed the event's public tick; the user changed this because the editor has no per-meetup tick.)
- **Static mode:** `staticBackend` loads `events.json` (a list of Leek Duck `ld` records) and `public.json`, then merges in memory, in layers, with `applyLayer()`:
  1. the snapshot;
  2. published edits (mark `published`);
  3. the visitor's own changes from localStorage `pogoCalendarMine`, in the same shape (mark `local`).

  Visitors edit only that third layer. "Undo my changes" removes their patch. Deleting their own event removes it, and "Hide from my view" on an owner event stores `{deleted: true}`. `edited` is recomputed against `ld` after each layer.
- **Export / Import:** both modes. Export saves "my changes" as a file in the `public.json` shape (`kind: pogo-calendar-changes`); in owner mode it's built from the store. Import goes through the current backend:
  - user events are added as new;
  - patches apply to events this view knows;
  - days merge: rest is OR'ed, notes are appended, and targets are added without duplicates.

  So the owner can import a visitor's suggestions into the private store, then tick the ones worth publishing.
- **Export scope:** visitors export their own layer. The owner chooses "all my changes" or "only what I've made public" (`ownerLayer(publicOnly)`).
- **Authorship:** the Export dialog takes an optional name (localStorage `pogoCalendarAuthor`), saved as `author` in the file. It isn't verified. Import then:
  - tags what it adds with `from`, on imported events and on each imported Pokémon;
  - prefixes imported notes with "Name: ";
  - adds imported Pokémon to an event's existing list instead of replacing it.

  Cards show "from Name", and tooltips "Suggested by Name".
- **Owner review of what's public:** the **Public…** dialog lists every event and day ticked public, each with a "Make private" button.
  - It compares `GET /api/public` (what would be published now) with `public/public.json` and says whether Publish is needed.
  - **Preview public site** swaps the page to `publicView()`: the Leek Duck copies plus the public-only layer, the same merge as the static site, with editing off. The owner's own data stays in `ownerData` until they leave the preview.
- **Building:** `tools/build_site.js` writes `site/`:
  - the page, plus a copy as `index.html`;
  - `public.json`;
  - `events.json` (`{generatedAt, events}`);
  - `icons/`, named by `lib/iconfile.js`, the same rule as `iconFile()` in the page.

  The icons are same-origin, so the page can crop them. Missing ones are copied from `data/icons` or fetched at 5/s. In static mode the page loads `icons/<file>` and falls back to the CDN for icons the site doesn't ship. `--from-store` builds from the local store; otherwise it scrapes, with `--known` (the previous `events.json`, a file or URL) so only new or stale detail pages are fetched. Events that dropped off Leek Duck's list are carried over from `--known` for 90 days after they end (`KEEP_DAYS`), the way the local store keeps history.
- **GitHub Actions** (`.github/workflows/pages.yml`):
  - schedule: every 6 h, on push, and by hand;
  - `site/icons` is kept in the Actions cache;
  - the previous snapshot is read from `vars.SITE_URL` + `events.json`;
  - deployed with `actions/deploy-pages`, so a run never commits to the repo.

  `data/` and `site/` are in `.gitignore`, so the owner's private store never reaches GitHub.
- **Preview locally:** `node tools/serve_static.js`, then http://localhost:8643/?static.
- **Keeping this PC private:** `tools/check_public.js` scans what would be published, plus the built `site/`, for drive paths, user folders, e-mail addresses and the personal patterns in the git-ignored `private-patterns.txt`. It also fails if `handover.md`, `data`, `start.local.bat`, `private-patterns.txt` or `.svn` stop being git-ignored. `start.bat` reads machine-specific settings from the git-ignored `start.local.bat`.

## Page

- **Data source:** the API base is `http://localhost:8642` when the page is opened from disk, otherwise the same origin. The last good `/api/events` result is kept in localStorage (`pogoCalendarCache`). When the server can't be reached, the page renders that copy and disables editing.
- **Home time:** all times are shown in SGT (`HOME` in `calendar.js`), and calendar days are SGT days. A zone-less Leek Duck time is read as wall-clock time in the event's zone. That zone is the user's `tz` override, or the zone of a city named in the title (the `CITIES` table; titles containing "Global" never match), or else SGT.
- **Overseas events:** an event whose zone isn't SGT is overseas. It gets a periwinkle day, a "✈ name" line, a "remote" tag, and times in SGT followed by the city's own time. Tooltips explain the access:
  - raids need a Remote Raid Pass;
  - Max Battles need a remote host in the event's city;
  - spawns are in person only;
  - special backgrounds are usually not available through remote raids.
- **Tiers** (`autoTier()`, overridable per event with `tier`):
  - *super*: Community Day, Wild Area, GO Tour, GO Fest, City Safari. The day is orange, with the name on top.
  - *major*: Raid Hour, Spotlight Hour, Raid Day, Max Battle Day, Max Monday, Hatch Day, Research Day. Big icons.
  - *weekly*: raid-battles rotations, and multi-day non-"event" types with raid bosses. Small icons in the bottom-right corner, plus a bar.
  - *minor*: everything else, shown in the day panel only. Multi-day `event`-type ones also get a bar. Exception: Pokémon the user starred or added go on the cell as big icons (events of up to 14 days), and such a day isn't "mundane".
  - **Cell icon order** (`dayInfo()`, first wins when two events list the same `monKey`): starred meetup targets, starred day targets, starred Pokémon of any event that day (any tier, events of up to 14 days), then the other meetup targets, the other day targets, super / major events, minor events' user Pokémon, and weekly rotations in the corner. So a starred Pokémon is shown from the event it was starred in, even when a bigger event that day lists it too (Zacian starred in Into the Wild vs the Mexico City Wild Area, 9 Nov).

  Super and overseas events show only raid bosses, Community Day stars (`cd`), valuable and user-added Pokémon on the cell; their full spawn lists stay in the day panel.

  Within a tier, the user's own events come first (`mineFirst`), on the cell and in the day panel.
- **Day backgrounds**, in order of precedence:
  1. rest (pale green, the user's flag);
  2. super (orange);
  3. overseas (periwinkle);
  4. mundane (pale grey): no super or major event, no user targets, and no weekly Shadow legendary or starred Pokémon.
- **Grid:** weeks start on Monday. Each week is a 7-column CSS grid. Cells span all its rows, and bars sit in lanes 2… along the bottom (at most 4 lanes, set by `--lanes`). Each Max Monday with a Pokémon also gets a Monday–Sunday bar in the Dynamax colour (`maxWeekBars()`), because its Dynamax Pokémon stays in Max Battles all week; clicking it edits the Max Monday event. It's the lowest-priority bar, in the bottom lane, unless its Pokémon is legendary / mythical / Ultra Beast, which puts it in the top lane (`barRank()`). Either way it always gets a lane: other bars leave one free for each week bar still to be placed. Cells pad their bottom by the lane height. A cell shows up to 6 big icons, then "+n", plus at most 5 small corner icons. Sat/Sun cells get a 2px `--weekend` outline, and their column headers are bold.
- **Season events:** events longer than 14 days (`SEASON_DAYS`) never put Pokémon on cells. They are listed in the collapsed "Running this month" section, with their valuable icons.
- **Icons:**
  - each icon tries a chain of candidates until one loads (`cdnIcons()`):
    1. the Pokémon's own Leek Duck icon;
    2. the icon the same name has in any scraped event (so a target "Gigantamax Duraludon" gets the event art);
    3. the form sprite `pm<dex>.f<FORM>.icon.png`, built from the name ("(Crowned Shield)" → `CROWNED_SHIELD`, "Mega … X" → `MEGA_X`, "Alolan" → `ALOLA`, a trailing "Forme"/"Form" dropped), from Leek Duck, then PokeMiners' `pogo_assets` (same names, CORS-open);
    4. the base species sprite `pm<dex>.icon.png`, then the old `pokemon_icon_<dex>_00.png`, which newer species lack.

    The server remembers CDN 404s for a day, so the chain doesn't keep asking. The static site ships every featured icon, base sprites for featured species, and all legendary / mythical / Ultra Beast base sprites.
  - each icon is cropped to its visible pixels on a canvas, then cached as a data URL, because Leek Duck sprites have uneven padding that made small species tiny. This needs the icon proxy's CORS header (or same-origin icons on the static site);
  - the pin goes bottom-right, a ✦ sparkle top-right for shiny, "BG" bottom-left for a special background, a padlock top-left for a region lock, a wireframe globe on the left edge for a Location Background (`globePin()`), and a "NEW" tag top-centre for a debut (gold for a shiny debut). On super / overseas day cells, debuts are shown next to raid bosses and valuable Pokémon, sorted right after the user's own. A Pokémon listed both in a feature blurb (`event`) and with a real activity is shown once, as the latter (`eventPokemon()`). The cell, event boxes and both tooltips all use that rule. Event boxes and bar tooltips order Pokémon with `monRank()`: the user's own, then raid bosses, debuts and valuable ones.
  - user-added Pokémon (`mine`) can be starred, which shows a two-arc rainbow swirl adapted from the Cluedo current-player token, and can carry a tooltip comment.
- **Meetup mark:** a day with any trainer meetup gets one map pin (`meetPin()`, colour `--meet`) right after the day number (`.daynum`), with a count when there are several. A meetup counts on every day from its start date to its end date (`onMeetDay()`): an end at 00:00 doesn't count that day, spans are capped at 14 days, and a meetup without a start counts on its event's first SGT day only. Hovering the pin shows that day's meetups, each with its own targets (starred first, ★, small icons: `meetMons()`), its event and times (`MEET_TIP`, `meetTipContent()`). Event boxes and bar tooltips list the event's meetups (`meetLines()`). A cell icon's tooltip (`TIP` entry with `day`, set by `cellMon()`) lists every meetup of that day, with the event's name when it's another event (by id or title, so the icon's own event isn't repeated). A day target that is also one of that day's event Pokémon (same `monKey`) hides the event's icon, so `dayInfo()` gives the target that event, and its tooltip then shows the event block and no repeated name. Elsewhere the Pokémon tooltip lists its own event's meetups.
- **Meetup editor** (`hostsEditor()`): host, venue and × on the first line, start and end on the second, the venue's map link on the third. Venues of all meetups so far are offered as suggestions (`datalist#venueNames`), and on leaving the venue box an empty map link is filled from a known venue of the same name (case and spacing ignored); a link already typed is never replaced. A new meetup, and an existing one with an empty time, takes the event's start / end as currently in the form, converted to SGT. A fourth part is the meetup's own target list (`hosts[].pokemon`, the same editor as day targets: star, comment): those Pokémon show on the cell only on the meetup's days, with "Target for the meetup: Host @ Venue" in their tooltip (the cell entry carries `meetup`).
- **Attending** (`going: true` on a meetup): right-click a day's meetup pin (`goingFromPin()`) toggles it when that day has one meetup, or opens the day panel when it has several; each meetup line in the day panel has an "Attending?" / "✓ Attending" button (`toggleGoing()`). An attended meetup circles the day's pin (`.meet.going`) and adds "✓ attending" in tooltips (`meetText()`). It's private: `Store.publicSnapshot()` and `ownerLayer(true)` strip `going`, so neither `public.json`, the public preview nor a public-only export shows it.
- **Rich tooltip:** a single floating `#tip`. It shows a 96px icon, name, shiny, activity, class, and the hundo catch CP. That's level 20, plus level 25 weather boosted, except for Max Battles, which show level 20 only. The CP is computed from the form's base stats in `pokedex.js`, which come from pogo-stats-comp's `data.js`. The tooltip also shows the event and its times, remote notes, who suggested it, and the user's comment.
- **Event name tooltip:** event names on the calendar show the event's day-panel box (`evCard(ev, true)`, without the Edit button or link) as a tooltip (`EV_TIP`, class `evtip`). That covers super-day and ✈ overseas names, each major-event line in a cell, and the "Running this month" chips. The box keeps its tier colours. The day panel builds its boxes with the same `evCard()`, and both now also show the Spotlight bonus.
- **Event bar tooltip:** bars use the same floating `#tip` (`BAR_TIP`, `barTipContent()`), not a plain `title`. On top are big cropped pictures of the first (up to 3) Pokémon: 96 px for one, 72 px for two or three. A Max Monday week bar instead shows exactly its Max Monday icon's tooltip, plus "In Max Battles all week: <Mon> – <Sun>". For other bars, below the pictures come the event's pin, title, tier and times, the overseas city, up to 8 Pokémon (raid bosses and valuable ones first) with pin, types, shiny and class, then the bonus, the note and who suggested it. There's no "click" hint: the tooltip vanishes when the mouse leaves the bar, so it would only mislead (clicking the bar itself opens the editor).
- **Types** come from `pokedex.js`: each form carries its types (from pogo-stats-comp's `data.js`), and each species its Mega / Primal type overrides (game master `tempEvoOverrides`, keys `MEGA`, `MEGA_X`, `MEGA_Y`, `PRIMAL`). Chips use the standard Pokémon GO type colours (`TYPE_COLORS`). The user's reference for these colours, `data/PoGo Mega 4s.pdf`, couldn't be rendered here, so the standard palette was used.
- **Super Max Level (Mega Level 4):** `SUPER_MAX` in `calendar.js` lists the Megas that can reach it, with their extra Charged Attack, from the fandom wiki's "List of Pokémon that can reach Super Max Level" (checked 2026-10-26). Update it by hand when new ones are added. Every Mega's tooltip says whether it can.
  - Unlocks are dated: `SUPER_MAX_FROM` holds announced days (Mega Sableye: 2026-11-01), and a Super Mega Raid Day unlocks its featured Mega from that SGT day on, inclusive (e.g. Chandelure, 31 Oct). `superMaxInfo()` compares the unlock day with the event's window: unlocked before it starts, "unlocks … during this event", or "unlocks …" later. Day targets with no event use the current time.
- **Spotlight Hour bonus:** the scraper reads "the special bonus is …" from the page prose into the Leek Duck copy's `bonus` (`ld.bonus`, or `bonus` on the static site's records). The tooltip shows it as "Bonus: …" for any event that has one.
- **Region-locked Pokémon:** a padlock sits top-left on the icon, teal for the home region (`HOME_REGIONS`: apac, east) and orange for another region.
  - For a local-time event, `regionWindows()` converts the event's wall-clock window in each sample place of `REGIONS[...].zones` into SGT. The tooltip shows the first-start to last-end span plus each place, and the day panel adds one line per locked Pokémon.
  - Example: Dynamax Mesprit (EMEA), 2–5 pm local, is live Sat 4:30 pm (India) to Sun 2:00 am SGT (Cape Verde).
  - The region can also be set per Pokémon in the editor.
- **Add Pokémon list:** species names plus "Name (Form)" for species with several forms. The form in brackets picks the stats for the hundo CP.
- **Help and welcome:** a **?** dialog explains the calendar, drawing the real pins and marks. On the public site, a one-time welcome note (localStorage `pogoCalendarWelcomed`) says visitors' changes stay in their browser and mentions Export.
- **Preferences:** month, event bars, and hidden activities are kept in localStorage (`pogoCalendarPrefs`). `#YYYY-MM` in the URL opens that month.
- **No browser dialogs:** deleting or undoing needs a second click on the same button.
- **Day panel:** while it's open, clicking any date closes it (the next click opens that day). Its header with × stays pinned at the top while the panel scrolls. The event link says "Info page", because it isn't always Leek Duck's.
- **Speed:** time-zone conversion keeps one `Intl.DateTimeFormat` per zone. It caches offsets per zone and UTC half hour (offsets only change on half-hour boundaries), and display formatters per zone and options. `evRange()` is memoized per event object, keyed by its times, title and zone. Opening a day only moves the `selected` class and fills the panel. Measured on November 2026 in headless Edge: a full render went from 4.8 s to 91 ms, and a day click from 4.6 s to 5 ms.
